## 0. Что изменилось в коде (кратко)

Сравнение с состоянием **ветки `9.5-Load+Restart-from-Checkpoint`** (checkpoint, Continue, Restart уже работают; **внешних gameplay-модулей в проекте ещё нет**).

В teacher repo добавлен **учебный пример интеграции готового пакета** (Dead-Simple Dialogue) через тонкий слой адаптеров. Этап **не обязует** повторять именно dialogue у всех — цель урока: **методика** выбора, импорта, проверки и стыковки с core loop. Dialogue в репозитории — **reference case**, чтобы было что открыть в Editor и Play Mode.

### Добавлено

- **`Assets/Dead-Simple Dialogue/`** — импортированный пакет (скрипты, Demo, PDF-документация). Demo-сцены и demo-скрипты — **reference**, в build учебного flow не обязательны.

- **`Assets/_Scripts/NPCs/EncounterNpcActivator.cs`** — связывает модуль с core loop: после **`EventBus.OnEncounterCompleted`** активирует NPC на gameplay-сцене.
- **`Assets/_ScriptableObjects/NPCs/Cutscenes/`** — `GuideDialogue.asset`, `Characters.asset`; текст сценария в **`GuideDialogue.txt`** (источник для генерации asset, не хранение текста в C#).
- **`Assets/_Prefabs/NPCs/NPCBase.prefab`** — SphereCollider (trigger), компонент **`NPCDialogueTrigger`**, ссылка на dialogue asset.
- Арт/анимация NPC: **`Assets/_Art/...`**, **`NPCController.controller`**.

### Изменено

- **`Assets/_Scripts/UI/PauseController.cs`** — отложенная подписка на **`EventBus`** и **`InputManager`** через корутину **`BindDependenciesWhenReady`** (после импорта пакетов порядок появления singleton может сдвинуться; без этого пауза иногда «молчит»).
- **`Assets/_Scenes/Levels/GameScene.unity`** — экземпляр **`NPCBase`** (позиция, стартовое **`m_IsActive: 0`** до encounter), переименование **`EncounterTrigger_Lesson7.4`** → **`EncounterTrigger`**.

### Зависимости и настройки проекта

- **`Packages/manifest.json`** — без новых UPM-пакетов от dialogue-импорта (лишние зависимости, если появятся при другом импорте, нужно **удалять вручную** после сверки с документацией пакета и версией Unity 6).
- **Project Settings** (URP, Color Space, Quality, Build Settings) — в этой ветке **не должны** меняться из-за dialogue; при любом импорте ассета обязателен **ручной аудит** (см. §3.4).

### Намеренно вне scope этого этапа в teacher repo

- Полные модули **Inventory**, **Loot**, **Quests** (в коде `_Scripts` пока нет — только dialogue как образец интеграции).
- Переписывание vendor-кода пакета (кроме локального `#if UNITY_EDITOR` в **`DialogueStructs.cs`** для безопасной сборки).

## 1. Зачем этот этап

### 1.1. Проблема, которую решает урок

Собственный код проекта (игрок, враги, encounter, UI, save) уже занимает много времени. На оставшихся занятиях **нереалистично** с нуля написать полноценные dialogue-, inventory- или quest-системы. При этом по спецификации курса в финальном vertical slice нужен **хотя бы один дополнительный модуль** из четырёх: Inventory, Loot, NPC+Dialogue, Quests.

Готовые пакеты (Asset Store, GitHub, `.unitypackage`) дают **готовую логику**, но **не встраиваются сами**:

- они не знают про **`EventBus`**, **`GameManager`**, **`PlayerProgression`**;
- они могут сбросить **URP**, **Input System**, **manifest**;
- они часто тянут **Demo-сцены**, лишние зависимости и Editor-only код;
- без чтения **документации** легко подключить «не тот» масштаб (целый RPG-framework вместо одной фичи).

Этот этап учит **интегрировать минимально полезный срез**: модуль **виден в игре**, **связан с core loop**, **не ломает** паузу, бой и загрузку сцен.

### 1.2. Чем этап отличается от «урока про диалоги»

| Фокус урока 9.6 | Не является главной целью |
|------------------|---------------------------|
| Как **выбрать** пакет по размеру и рискам | Как устроен внутренний парсер Dead-Simple Dialogue |
| **Чеклист до/после импорта** | Полировка UI окна диалога |
| Паттерн **адаптера** (glue-код проекта) | Квесты, ветвления, inventory UI |
| **Стыковка с событием** encounter | Сохранение состояния NPC в checkpoint |
| **Документация пакета** как первый источник правды | Копирование teacher repo 1:1 |

В teacher repo dialogue — **живой пример** для демонстрации на занятии, а не единственный допустимый модуль.

### 1.3. Ожидаемый результат этапа (Definition of Done)

После разбора и практики в **своём** проекте должно быть достижимо:

1. Выбран **один** внешний модуль (inventory / loot / dialogue / quests — по желанию).
2. Пакет **импортирован** без поломки compile, URP и базового flow (**Bootstrap → Menu → Game**).
3. Есть **1–3 скрипта-адаптера** проекта (не массовые правки vendor).
4. Контент модуля (тексты, предметы, квесты) лежит в **asset/данных**, а не в строках в `Update`.
5. Модуль **включён в геймплей**: хотя бы одна понятная точка (после encounter, при подходе к NPC, при луте с врага и т.д.).
6. Пройден **mini smoke-test** (§6) без новых ошибок в Console.

## 2. Документация пакета — обязательный первый шаг

> **Важно.** Пропуск документации — самая частая причина потери 1–3 занятий на «чиним проект после импорта». Любой импорт начинается с **чтения документации**, а не с перетаскивания prefab в сцену.

### 2.1. Где искать документацию

| Источник | Что там обычно есть | Зачем читать |
|----------|---------------------|--------------|
| **PDF / README** в папке пакета | Быстрый старт, ограничения, версия Unity | Понять, подходит ли пакет под Unity 6 + URP |
| **Demo-сцена** пакета | Эталон «как автор задумал» | Увидеть обязательные объекты и порядок настройки |
| **Страница Asset Store / GitHub** | Совместимость, зависимости, лицензия | Не скачать GPL/некоммерческую лицензию по ошибке |
| **Комментарии в коде пакета** | Скрытые требования (TMP, Input System) | Предсказать конфликт с текущим проектом |
| **Официальная вики Unity** (URP, Input System) | Если пакет меняет pipeline | Откатить не те настройки осознанно |

В teacher repo для case study: **`Assets/Dead-Simple Dialogue/Dead-Simple Dialogue Documentation.pdf`** — прочитать **до** правок в `GameScene`.

### 2.2. Что именно выписать из документации (мини-конспект)

Перед импортом в рабочую ветку заполнить (на бумаге или в заметках):

1. **Минимальная версия Unity** и render pipeline (Built-in / URP / HDRP).
2. **Обязательные зависимости** (TextMeshPro, Input System, Newtonsoft и т.д.).
3. **Обязательные объекты в сцене** (Manager, Canvas, EventSystem, Bank).
4. **Формат данных** (ScriptableObject, JSON, ScriptableWizard, текстовый `.txt`).
5. **API входа** — один главный метод/компонент для старта фичи (в dialogue: `DialogueManager.StartNewDialogue(Cutscene)`).
6. **События завершения** (в dialogue: `OnDialogueEnded`) — куда вешать награду/квест.
7. **Известные ограничения** (нет save, нет multiplayer, только 2D и т.д.).
8. **Что автор считает Demo** — можно не включать в build.

Если в документации **нет** ответа на пункт 3 или 6 — пакет для учебного срока **высокого риска**.

### 2.3. Почему Demo-сцена — не «готовый уровень проекта»

Demo собрана автором пакета под **свои** имена сцен, камеру и input. Перенос Demo в `GameScene` целиком:

- ломает **канон сцен** проекта (`Bootstrap`, `MainMenu`, `Loading`, `GameScene`);
- создаёт **второй** `EventSystem`, `AudioListener`, `DialogueManager`;
- отвлекает от задачи: **адаптер + одна точка в своём flow**.

Правильный путь: Demo **открыть один раз**, посмотреть связи в Inspector, затем повторить **минимум** в своей сцене или через runtime-bootstrap (как `DialogueRuntime`).

### 2.4. Документация vs «смотреть только код пакета»

Код пакета показывает **как сделано**, но не всегда **что обязательно для запуска**. Документация фиксирует контракт автора. При расхождении:

- для интеграции верить **документации и Demo**;
- Reflection и хаки — только как **временный** glue (см. `DialogueRuntime`), с комментарием о риске обновления пакета.

## 3. Из чего состоит интеграция и как связаны части (карта)

### 3.1. Три слоя (универсальная схема)

```text
┌─────────────────────────────────────────────────────────────┐
│  ВНЕШНИЙ ПАКЕТ (vendor)                                      │
│  DialogueManager, Cutscene, UI пакета, Demo…                 │
│  Автор обновляет API — проект не «владеет» этим кодом        │
└───────────────────────────┬─────────────────────────────────┘
                            │ вызывается только через узкий API
┌───────────────────────────▼─────────────────────────────────┐
│  АДАПТЕР ПРОЕКТА (glue, 1–3 класса)                          │
│  DialogueRuntime.EnsureReady()                               │
│  NPCDialogueTrigger — ввод игрока + запуск Cutscene          │
│  EncounterNpcActivator — когда показать NPC                  │
└───────────────────────────┬─────────────────────────────────┘
                            │ события / награды / условия
┌───────────────────────────▼─────────────────────────────────┐
│  CORE LOOP ПРОЕКТА                                           │
│  EventBus.OnEncounterCompleted → NPC → диалог → XP           │
│  GameManager, PlayerProgression, Pause, EncounterTrigger     │
└─────────────────────────────────────────────────────────────┘
```

**Почему три слоя:** пакет можно обновить или заменить, меняя в основном адаптер. Core loop остаётся стабильным для других уроков.

### 3.2. Карта teacher repo (case study: dialogue)

| Компонент | Роль | Связи |
|-----------|------|--------|
| **`EncounterTrigger`** | Завершает encounter, вызывает **`EventBus.RaiseEncounterCompleted`** | Уже существующий core |
| **`EncounterNpcActivator`** | Слушает **`OnEncounterCompleted`**, включает **`NPCBase`** | Не меняет `EncounterTrigger` |
| **`NPCBase` + `NPCDialogueTrigger`** | Trigger, **E**, поле **`dialogueAsset`** | `Cutscene` из пакета |
| **`DialogueRuntime`** | Готовит **`DialogueManager`** + UI | Вызывается перед стартом диалога |
| **`GuideDialogue.asset`** | Текст и реплики | Создан из **`GuideDialogue.txt`** |
| **`PlayerProgression`** | XP после диалога | Только в адаптере, пакет о XP не знает |
| **`PauseController`** | Пауза после импорта | Отложенная подписка на singleton |

### 3.3. Таблица: какой модуль к чему стыкуется (для своего проекта)

| Модуль | Минимальный срез | Типичная точка стыковки с core loop |
|--------|------------------|-------------------------------------|
| **NPC + Dialogue** | 1 NPC, 1 диалог, 1 награда | После encounter / у выхода |
| **Loot** | 1 таблица дропа, 1 pickup | **`EnemyDeathRewarder`** / смерть врага |
| **Inventory** | 1 предмет, открытие UI по клавише | После loot или у сундука-trigger |
| **Quests** | 1 квест «убей N» / «поговори» | **`OnEncounterCompleted`** / **`OnDialogueEnded`** |

За один учебный модуль достаточно **одной строки** в таблице — не всех четырёх.

Каждый крупный шаг — в трёх слоях. Порядок **обязателен**: сначала выбор и документация, потом импорт и аудит, потом адаптер и сцена.

### 4.1. Выбор пакета: не брать «целый мир»

**Editor**

**Check**

**Почему так (пример из разбора teacher repo):**

| Пакет | Вердикт | Причина |

| **Dead-Simple Dialogue** | Подходит как учебный | Узкая фича, мало связей с боем |
| **AnyRPG Core** | Отклонён | Целый RPG-framework, конфликт архитектуры |

### 4.4. Аудит проекта после импорта (обязательный чеклист)

> **Важно.** Импорт ассета часто меняет **глобальные** настройки. Даже если «всё скомпилировалось», игра может стать розовой, тёмной или без паузы.

**Editor**

| Что открыть | Что проверить | Почему это ломается |
|-------------|---------------|---------------------|
| **Edit → Project Settings → Graphics** | Scriptable Render Pipeline = **URP asset проекта** | Импорт подставляет другой pipeline |
| **URP Asset** (в Project) | Тот же asset, что до импорта | Сброс quality/shadows |
| **Player → Color Space** | **Linear** (как в каноне курса) | Gamma меняет освещение |
| **Packages/manifest.json** | Нет лишних `com.unity.*`, которых не было | Пакет тянет несовместимые версии |
| **File → Build Settings** | Сцены **Bootstrap, MainMenu, Loading, GameScene** | Demo-сцена могла добавиться в build |
| **Input System** | Active Input Handling как в проекте | Пакет может требовать Both/Old |
| **TextMeshPro** | Essentials импортированы, если пакет UI на TMP | Пустые квадраты вместо текста |

**Code**

- Открыть **`Packages/manifest.json`** в IDE: сравнить с веткой **до** импорта (`git diff`).
- Если пакет добавил **`using UnityEditor`** в runtime-скрипты — обернуть в `#if UNITY_EDITOR` **только при необходимости** (в teacher repo: `DialogueStructs.cs`).

**Check**

- Запуск **своей** `GameScene` (не Demo): освещение нормальное, UI читаемый.
- **Pause** открывается с клавиши (после фикса **`PauseController`** в ветке 9.6).
- `git diff ProjectSettings` — осознанные изменения или откат лишнего.

**Зачем отдельный шаг:** в ветке 9.6 URP/manifest не должны были измениться; на занятии показать, **что именно** смотреть при **любом** следующем импорте.

### 4.6. Проектирование адаптера (glue-код)

**Editor**

- На доске нарисовать: **событие core** → **адаптер** → **один вызов API пакета** → **награда/флаг**.

**Code**

Принципы (обязательные):

1. **Имена классов проекта** — свои (`DialogueRuntime`, не `Lesson15...` в финале).
2. **Публичный API пакета** — вызывать напрямую где возможно; Reflection — только с комментарием о риске (см. `DialogueRuntime.SetPrivateField`).
3. **Данные** — `[SerializeField]` на **asset пакета** (`Cutscene`), не `string[]` в коде.
4. **Подписки** — `OnEnable`/`OnDisable` или корутина ожидания singleton (`EncounterNpcActivator`, `PauseController`).
5. **Награды и квесты** — только в адаптере после **события пакета** (`OnDialogueEnded`).

**Check**

- Новых классов **1–3**, не «папка на 20 файлов».
- `EncounterTrigger` и `GameManager` **не** раздуваются логикой диалога.

**Почему:** спецификация курса запрещает god objects и ломание существующих контрактов.

### 4.8. Case study: NPC и trigger в сцене

**Editor**

1. Префаб **`Assets/_Prefabs/NPCs/NPCBase.prefab`**:
   - **SphereCollider**, **Is Trigger** = true, радиус ~3 (настройка зоны «поговорить»).
   - Компонент **`NPCDialogueTrigger`**, поле **`dialogueAsset`** → `GuideDialogue.asset`.
   - **`experienceReward`** (например 50) — опциональная связь с progression.
2. **`GameScene`**: экземпляр NPC, **`m_IsActive` = false** до encounter (активатор включит после волны).
3. Игрок: tag **`Player`**, CharacterController + collider для входа в trigger.

**Code**

- **`NPCDialogueTrigger`**: `OnTriggerEnter/Exit` + **E** в `Update` (учебное упрощение; не блокирует паузу автоматически — осознанный trade-off).
- **`playOnlyOnce`**: один диалог за сессию.

**Check**

- До encounter NPC **не виден** (или неактивен).
- После encounter: NPC появляется, в зоне trigger — по **E** открывается окно.
- **Space / Enter / ЛКМ** листают реплики (`DialogueRuntime.Update`).

**Почему trigger + тег:** стандарт Unity; типичная поломка — NPC без trigger или игрок без tag `Player`.

### 4.9. Case study: связь с encounter (core loop)

**Editor**

- На сцене **`EncounterTrigger`** с волной, которую можно завершить в Play Mode.
- Убедиться, что в сцене есть объект с именем **`NPCBase`** (или назначен **`npcOverride`** на **`EncounterNpcActivator`** — поле опционально в коде).

**Code**

- **`EncounterTrigger`** по завершению вызывает **`EventBus.RaiseEncounterCompleted(encounterId)`** — **не менять** для dialogue.
- **`EncounterNpcActivator`**: `[RuntimeInitializeOnLoadMethod]` создаёт объект на всю игру; **`BindEventBusWhenReady`** ждёт **`EventBus.Instance`**.
- При событии: **`sceneNpc.SetActive(true)`**, **`DialogueRuntime.EnsureReady()`**.

**Check**

- Пройти encounter → в Console лог активации NPC (если включён).
- NPC появляется **только после** победы над волной, не при старте уровня.

**Зачем:** модуль «в игре», а не в меню Settings — требование vertical slice и урока 15–16 маршрута.

### 4.10. Case study: bootstrap UI пакета (`DialogueRuntime`)

**Editor**

- Если в `GameScene` **нет** готового `DialogueManager` с Canvas из Demo — при первом диалоге появится объект **`Dialogue Runtime`** (DontDestroyOnLoad).

**Code**

- **`DialogueRuntime.EnsureReady()`** — idempotent: второй вызов не дублирует manager.
- Создаёт Canvas, TMP, **`CharacterBank`** в runtime — **учебный минимум**, не финальный art.
- **Reflection** в **`EnsureDialogueManager`**: при обновлении пакета проверить имена private-полей.

**Check**

- Первый диалог в сессии создаёт UI; второй NPC использует тот же manager.
- Console без `DialogueRuntime: поле ... не найдено`.

**Почему не prefab из Demo:** меньше ручной сборки на занятии; в своём проекте можно заменить на prefab из документации — это **улучшение**, не обязанность.

### 4.11. Награда после модуля (стыковка с progression)

**Editor**

- На компоненте **`NPCDialogueTrigger`**: **`experienceReward > 0`**.

**Code**

- **`HandleDialogueEnded`**: сравнить `endedCutscene` с назначенным asset; один раз вызвать **`PlayerProgression.AddExperience`**.
- Пакет **не** знает про XP — только адаптер.

**Check**

- HUD XP/Level обновился после последней реплики.
- Повторный диалог с **`playOnlyOnce`** не даёт XP второй раз.

### 4.12. Регрессии после импорта: пауза и порядок singleton

**Editor**

- Play Mode: **Pause** во время gameplay, **Resume**, **Main Menu**.

**Code**

## 5. Частые ошибки и хрупкие места

### 5.1. Импорт и настройки

| Симптом | Вероятная причина | Что сделать |
|---------|-------------------|-------------|
| Розовые материалы | Сбит URP asset | Graphics → URP asset проекта |
| Всё слишком тёмное/яркое | Color Space | Player → Linear |
| Ошибки пакетов UPM | manifest раздут | `git diff manifest.json`, удалить лишнее |
| Demo запускается вместо игры | Demo в Build Settings | Убрать лишние сцены из build |

### 5.2. Collider, trigger, слои

| Симптом | Причина | Проверка |
|---------|---------|----------|
| E не реагирует | Нет trigger / неверный collider | `isTrigger`, радиус, игрок с Rigidbody/CC |
| Trigger не срабатывает | Нет tag **Player** | Inspector игрока |
| Двойной ввод | Два EventSystem | Hierarchy на `GameScene` |

### 5.3. Lifecycle и события

| Симптом | Причина | Проверка |
|---------|---------|----------|
| Пауза молчит | Singleton ещё null в OnEnable | `PauseController`, порядок Bootstrap |
| NPC не появляется | Нет `OnEncounterCompleted` / неверное имя | `EncounterTrigger`, Console |
| Двойная XP | Две подписки `OnDialogueEnded` | `OnDisable` отписка |
| Диалог на мёртвом игроке | Нет проверки `GameState` | Осознанный trade-off; опционально блок в адаптере |

### 5.4. Данные и документация

| Симптом | Причина | Проверка |
|---------|---------|----------|
| Пустой диалог | `dialogueAsset` не назначен | Inspector NPC |
| Старый текст | Asset не пересобран из `.txt` | Меню Cutscenes from script |
| Ошибка после обновления пакета | Reflection / переименованы поля | Документация changelog пакета |

### 5.5. Архитектурные анти-паттерны (избегать)

- Хранить сюжет в C#-строках вместо asset.
- Править десятки файлов в `Assets/ThirdParty/...` под свой проект.
- Встраивать логику квестов в `EnemyBase` «потому что удобно».
- Тянуть **второй** модуль до завершения первого в vertical slice.

## 9. Краткая памятка (одна страница)

1. **Прочитать документацию** и выписать §2.2.
2. **Ветка + baseline** smoke core.
3. **Импорт** → Console clean → Demo в изоляции.
4. **Аудит** URP, manifest, Build Settings, Input, TMP.
5. **Не тащить Demo** в свой `GameScene` целиком.
6. **1–3 адаптера** + данные в asset.
7. **Стыковка с событием** core (`EventBus`, смерть врага, trigger).
8. **Smoke-test** §6.
9. При поломке — сначала **откат настроек**, потом код; снова открыть **документацию**, а не гадать по StackOverflow.

Документация пакета — не «рекомендация», а **обязательный** шаг интеграции готовых систем в проект.
