# Checkpoint system: сохранение прогресса (Save Game Free + JSON)

---

## 0. Что изменилось в коде (кратко)

Сравнение с состоянием **ветки `9.3`** (до темы checkpoint на диске). В teacher repo добавлена запись прогресса в **три слота** через пакет **BayatGames Save Game Free**, параллельно — **читаемый JSON** для smoke-проверки и разбора структуры данных. Загрузка после смерти, кнопка Continue и применение save к сцене — **вне scope** этого этапа (следующий этап).

### Добавлено

- **`Assets/_Scripts/Save/CheckpointSaveData.cs`** — модель данных checkpoint (это **`[Serializable]` класс**, не ScriptableObject: ассет в проекте не создаётся, объект собирается в runtime и сериализуется в файл/слот пакета).
- **`Assets/_Scripts/Save/CheckpointSaveSystem.cs`** — три слота с ключами `checkpoint_progress_0` … `checkpoint_progress_2`, запись/проверка/чтение через Save Game Free; **строгий** успех: `true` только если записались и слот пакета, и debug-JSON.
- **`Assets/_Scripts/Save/CheckpointJsonDebugExporter.cs`** — экспорт `checkpoint_slot_{0,1,2}.json` в `Application.persistentDataPath` через `JsonUtility.ToJson(..., true)`; проверка диапазона слота перед записью.
- **`Assets/_Scripts/Save/CheckpointTrigger.cs`** — второй вариант checkpoint: отдельная **safe-point** зона (trigger), опционально с правилами по encounter.

### Изменено

- **`Assets/_Scripts/Core/GameManager.cs`** — сбор данных вынесен в `TryBuildCheckpointData`; публичные сценарии: `TrySaveLevelCheckpointProgress` (выход уровня / win-path) и `TrySaveCheckpointProgress` (отдельная зона); для win на выходе **успешное сохранение обязательно** для согласованности с UI.
- **`Assets/_Scripts/UI/GameLoopFlowController.cs`** — поле `checkpointSlotIndex` (0..2), валидация в `Awake` с `LogError` и **runtime-clamp к 0** при ошибке; `RequestWinFromExit` **не** показывает win, если checkpoint не сохранился.
- **`Assets/_Scripts/UI/ExitWinTrigger.cs`** — передача позиции выхода в flow-контроллер для записи в данные.

### Зависимости проекта

- Пакет **Save Game Free** (папка `Assets/BayatGames/SaveGameFree/...`, namespace `BayatGames.SaveGameFree`).

## 1. Зачем этот этап

### 1.1. Что вообще значит «сохранить игру» (очень коротко)

Игра в Play Mode живёт в **оперативной памяти**. Как только закрыть игру или перезапустить сцену без специальной логики — **числа пропадают**: здоровье, опыт, «на каком уровне остановился».  
**Сохранение** — это превратить важные числа и строки в **запись на диск** (файл или несколько файлов), чтобы потом их **прочитать обратно**. Чтение и применение к сцене — **следующий этап**; здесь только **запись**.

---

### 1.2. Какие бывают сохранения (упрощённая «карта местности»)

Не существует одного слова «save» для всех студий. Удобно думать так:

| Тип | Что это в жизни | Пример в проекте курса |
|-----|------------------|-------------------------|
| **Настройки** | Громкость, полноэкранный режим — мало данных, почти не меняется структура | Этап 9.3: `PlayerPrefs` / `GameSettings` |
| **Checkpoint / прогресс** | «Запомни, где я в кампании»: сцена, уровень, базовые статы игрока | Этот этап: `CheckpointSaveData` |
| **Полный снимок мира** | Всё: каждый ящик, каждый враг, каждая пуля | **Вне канона** этого курса — слишком дорого и сложно |
| **Только в рамках одного запуска** | «Пока не выключил игру — помню», без файла на диске | Этап 9.2: перенос состояния игрока между сценами в `GameManager` |

**Checkpoint** в этом курсе — не «фотография всей сцены», а **короткая записка**: кто игрок (HP, мана, уровень, опыт, слот оружия), **в какой сцене** это было, **куда дальше** по списку уровней, **где стояла точка** сохранения. Такую записку проще проверить, проще загрузить в коде и проще объяснить на занятии.

---

### 1.3. Почему не сохраняем «активную волну» и бой посередине

Если сохранить момент, когда вокруг **живые враги**, летят **снаряды**, у encounter **свой внутренний таймер** и списки спавна, то при загрузке нужно **точно восстановить** всё это состояние. Один пропущенный объект — и уровень «ломается»: враг уже не тот, волна зависла, выход открылся раньше времени.

Поэтому в каноне курса сохранение привязано к **спокойной точке** (выход после выполнения условий или отдельная safe-зона по правилам дизайна). В save **не кладётся** «как сейчас идёт волна» — только **устойчивые** данные игрока и прогресс по уровням.

---

### 1.4. Что такое JSON — одной фразой и чуть глубже

**JSON** (JavaScript Object Notation) — это **текстовый формат**: человек может открыть файл в Блокноте и увидеть **фигурные скобки**, **названия полей** и **значения** вроде `"health": 85.5`.  
Это **не язык программирования** и не «магия Unity» — просто **договорённость**, как записать структуру данных строкой.

В Unity из коробки для простых классов часто используют **`JsonUtility`**: он берёт объект C# с пометкой **`[Serializable]`** и превращает его в JSON-строку (и обратно — когда понадобится загрузка).

---

### 1.5. Зачем две записи: пакет Save Game Free **и** отдельный `.json` файл

Здесь не «два разных save для игрока», а **одна и та же информация**, записанная **двумя способами** под **разные задачи**:

1. **Save Game Free** — готовый популярный инструмент: записывает данные в **свой** формат под капотом, даёт простые вызовы `Save` / `Load` / `Exists`, хорошо подходит для **настоящего** слота прогресса в учебном и коммерческом проекте.

2. **Файл `checkpoint_slot_0.json` (и 1, 2)** — **копия для глаз и для урока**:  
   - сразу видно, **что именно** попало в сохранение;  
   - можно открыть путь из лога и **показать файл** без специальных утилит;  
   - на занятии проще сказать: «вот поле `nextSceneName`, вот `playerLevel`».

В teacher repo сделано **строгое правило**: операция считается успешной только если **сработали оба шага**. Иначе легко получить ситуацию «вроде победил, а проверить нечем» — для smoke-проверки урока это хуже, чем честная ошибка в Console.

**Важный нюанс для преподавателя:** если пакет уже записал слот, а запись JSON упала (права, диск), метод вернёт `false`, но на диске **может** остаться обновлённый слот пакета. На уроке достаточно сказать: «смотрим Console и оба артефакта; при странностях — пересохранить после исправления».

---

### 1.6. Почему `CheckpointSaveData` — это не ScriptableObject в Project

**ScriptableObject** — это, как правило, **файл-настройка внутри проекта** (asset), который дизайнер кладёт в папку и правит в Inspector.

**Checkpoint** здесь — это **снимок во время игры**: его не обязательно хранить как `.asset` в репозитории. Достаточно **обычного класса** с `[Serializable]`: Unity и пакет умеют превратить его в байты/файл.  
Думать об этом как о **бланке формы**: во время игры бланк заполняется числами, потом бланк **сворачивают в файл**.

---

### 1.7. Итог: что должен вынести этап

- **Checkpoint** = маленькая **запись прогресса** в **безопасной точке**, без «всего мира» и без активной волны.
- **JSON** = **человекочитаемая копия** тех же полей для разбора и демонстрации.
- **Save Game Free** = **рабочий** слот сохранения, с которым потом свяжут загрузку.
- **Три слота** = задел под разные профили или сценарии без переписывания системы с нуля.

## 2. Из чего состоит система и как связаны компоненты (карта связей)

### 2.1. Данные

- **`CheckpointSaveData`** — поля: версия схемы, id checkpoint, текущая/следующая сцена и индексы уровня, позиция точки сохранения, флаг `savedFromLevelExit` (выход vs safe-point), HP/Mana/уровень/опыт/слот оружия.  
  **Важно:** это не ScriptableObject в AssetDatabase — это **DTO для сериализации** на диск.

### 2.2. Запись на диск

- **`CheckpointSaveSystem`** — единая точка: `Save(slot, data)`, `Exists(slot)`, `TryLoad(slot, out data)`; ключи слотов `checkpoint_progress_{0,1,2}`.
- **`CheckpointJsonDebugExporter`** — после успешной записи пакета создаётся `checkpoint_slot_N.json` в `Application.persistentDataPath`.

### 2.3. Кто инициирует save

1. **Выход уровня (win-path):** `ExitWinTrigger` → `GameLoopFlowController.RequestWinFromExit(position)` → при успешных проверках win → `GameManager.TrySaveLevelCheckpointProgress(checkpointSlotIndex, position)` → `CheckpointSaveSystem.Save`.  
   **Победа не показывается**, если save вернул `false` (в т.ч. если не создался JSON — см. раздел 5 и раздел 4).

2. **Отдельная safe-point зона:** объект с **`CheckpointTrigger`** + Collider **Is Trigger** → при выполнении правил зоны → `GameManager.TrySaveCheckpointProgress(slotIndex, position)`.

### 2.4. Связь с прошлым этапом (runtime между сценами)

- Перенос HP/XP/оружия **между сценами в одном запуске** делает `GameManager` через `pendingPlayerRuntimeState` (этап 9.2).  
- **Checkpoint на диск** — отдельный слой: переживает **закрытие игры** (после реализации загрузки в следующем этапе).

### 3.2. Три слота и поле `checkpointSlotIndex` на выходе уровня

**Editor**

**Check**

### 3.3. Сохранение на выходе уровня (win + обязательный успешный checkpoint)

**Editor**

- Убедиться, что **выход** настроен как раньше: `Collider` + **Is Trigger**, tag игрока, объект выхода активируется после encounter.
- На выходе — компонент **`ExitWinTrigger`**, ссылка на **`GameLoopFlowController`** назначена.
- В `GameLoopFlowController` заданы win/lose UI и при необходимости `requiredEncounterIdForWin` / `exitActivationObjectOverride` (как в этапе vertical slice).

**Code**

- Цепочка: `ExitWinTrigger.OnTriggerEnter` → `RequestWinFromExit(transform.position)`.
- `RequestWinFromExit`: после проверок win вызывается `GameManager.TrySaveLevelCheckpointProgress(checkpointSlotIndex, levelExitPosition)`; при **`false`** — предупреждение в Console, **win не вызывается**.
- `GameManager.TrySaveLevelCheckpointProgress` — собирает `CheckpointSaveData` с `savedFromLevelExit == true` и id вида `LevelComplete_{ActiveScene}`.

**Check**

- Пройти encounter, войти в выход: в Console — лог успешного сохранения слота Save Game Free и строка **`Checkpoint JSON written: ...`** с полным путём.
- Сломать условие save (например, временно убрать компонент с игрока): win **не** должен открыться, в Console — предупреждение про остановку win.

### 3.4. Debug-JSON: где файл и как им пользоваться в учебных целях

**Editor**

- После успешного save скопировать путь из лога `Checkpoint JSON written: ...` (это каталог `Application.persistentDataPath`, на Windows обычно что-то вроде `...AppData\LocalLow\<Company>\<Product>\`).
- Открыть файл `checkpoint_slot_0.json` (или `1` / `2` в зависимости от слота) в любом текстовом редакторе.

**Code**

- `CheckpointJsonDebugExporter` — `JsonUtility.ToJson(data, true)`; имена файлов: `checkpoint_slot_{0,1,2}.json`.
- **`CheckpointSaveSystem.Save`** возвращает **`true` только если успешны оба шага** (пакет + JSON). Если пакет записался, а JSON нет — в Console будет **предупреждение**, метод вернёт **`false`** (для урока JSON считается частью smoke-проверки).  
  **Нюанс:** в редком случае слот Save Game Free на диске уже мог обновиться до отказа JSON — об этом стоит помнить при ручной диагностике (см. раздел 4).

**Check**

- В JSON видны поля вроде `health`, `playerLevel`, `nextSceneName`, `checkpointPosition`, `savedFromLevelExit`.
- Попробовать **осторожно** изменить числовое поле, сохранить файл: на **этом** этапе игра **не обязана** подхватывать правки (загрузка и контракт полей — следующий этап). Цель шага — **понимание формата**, а не читы в релизе.

**Ограничения `JsonUtility` (коротко для методики)**

- Сериализуются **публичные поля** `[Serializable]` типа; нет «умной» поддержки словарей и полиморфных коллекций как в «большом» JSON.
- Ручное редактирование легко приводит к несовпадению с будущим кодом загрузки — для курса позиционировать как **отладка / демонстрация структуры**, не как игровой дизайн.

## 4. Частые ошибки и хрупкие места

- **Win не открывается после выхода** — сначала проверить Console: часто это **`checkpoint не сохранён`** (нет JSON, нет компонентов игрока, ошибка пакета). Это **ожидаемое** поведение: победа без доказуемого save не показывается.
- **Нет строки `Checkpoint JSON written`** — проверить права на запись в `persistentDataPath`, целостность пакета, полный вывод `CheckpointSaveSystem` (предупреждение про JSON).
- **Collider / trigger / tag** — как и у выхода: игрок должен иметь tag `Player`, коллайдер checkpoint — **Is Trigger**, слои должны допускать столкновение с игроком.
- **`GameManager` отсутствует на сцене** — `CanTriggerWin` не даст win; отдельный `CheckpointTrigger` залогирует отсутствие `Instance`.
- **Два игрока / дубликаты компонентов** — `GameManager` при сборе данных может предупредить и взять «первый найденный»; для стабильной демонстрации на сцене должен быть **один** корректный набор `PlayerStats` / `PlayerProgression` / `WeaponManager`.
- **Путаница ScriptableObject** — для checkpoint **не** создаётся `.asset` данных в проекте: модель — обычный serializable-класс для файла save.
