## 0. Что изменилось в коде (кратко)

Сравнение с состоянием **после этапа «Урок 9.5 — Загрузка и restart из checkpoint»** (и последующих этапов save/UI, если они уже влиты в проект).

**Этап 9.7 — прежде всего процессный:** диагностика производительности, Profiler, подготовка и сборка билда, release smoke-test. **Обязательных новых классов или систем в teacher repo для прохождения этапа не требуется** — используются уже существующие точки нагрузки и flow игры.

### Что используется как «учебные якоря» в коде (без обязательных правок)

- **`Assets/_Scripts/Enemies/EnemySpawner.cs`**, **`SimpleEnemySpawner.cs`** — спавн через **`Instantiate`**, список активных врагов, типичный источник **GC Alloc** при волнах encounter.
- **`Assets/_Scripts/Enemies/RangedEnemy.cs`** — **`Instantiate`** снаряда при каждой атаке.
- **`Assets/_Scripts/Enemies/EnemyBase.cs`** — **`Update`** для AI; **`Destroy`** после смерти (simple-ветка); заготовка под pool — проверка компонента **`PooledEnemy`** без жёсткой зависимости от advanced-ветки.
- **`Assets/_Scripts/Encounters/EncounterTrigger.cs`** — сценарий «много врагов за короткое время» для Profiler-записи.
- **`Assets/_Scripts/Core/GameManager.cs`**, **`SceneLoader`**, UI flow — полный проход от меню до win/lose для записи и для smoke-test билда.
- **`ProjectSettings/EditorBuildSettings.asset`** — список сцен для билда (в teacher repo: **`Bootstrap`**, **`MainMenu`**, **`Loading`**, несколько **`GameScene`** в **`Assets/_Scenes/Levels/`**).

### Опционально (бонус teacher repo / сильный уровень)

- Ветка **`enemies-advanced`** с **`EnemyPool`** / **`EnemyFactory`** — демонстрация pooling **без обязательной реализации у всех**; в simple-ветке достаточно понимать идею и увидеть комментарий в **`EnemyBase`** про **`PooledEnemy`**.
- Отображение **`Application.version`** на pause/HUD — по желанию, 1–2 строки в существующем UI-контроллере.

### Зависимости

- Unity **6000.0.50f1**, встроенный **Profiler** (Window → Analysis → Profiler).
- Отдельные пакеты для этапа **не обязательны**.

## 1. Зачем этот этап

К концу курса vertical slice уже **играется в Editor**, но демонстрация и «взрослая» проверка проекта требуют другого шага:

- **Editor ≠ билд:** другой рантайм, нет лишних оверхедов редактора, иные лимиты на слабом ПК или телефоне.
- **Производительность** — не «магия FPS», а **контроль опыта:** фризы ломают бой и encounter, рост памяти — вылеты, спам в Console — скрытые баги.
- **Билд** — формальный **quality gate:** игра запускается вне Unity, проходит тот же сценарий, что и на занятии, без сюрпризов на презентации.

Результат этапа: **releasable vertical slice** — не идеально оптимизированный AAA-проект, а проект с **осознанной диагностикой**, **одной осознанной микро-правкой** (по желанию) и **проверенным exe** (или согласованной платформой класса).

## 2. Из чего состоит «система» этапа и как связаны части (карта)

Этап не вводит один монолитный класс — это **цепочка инструментов и проверок**:

```text
Console (ошибки/шум)
    ↓
Profiler-запись (CPU / Rendering / Memory / Physics)
    ↓
3 красных флага → 1 микро-правка (опционально повторная запись)
    ↓
Pre-build checklist
    ↓
Development Build → exe
    ↓
Release smoke-test (в билде, не в Play Mode)
    ↓
Release note (версия, платформа, known issues)
```

### 2.1. Где в проекте искать нагрузку

| Область | Где смотреть в коде/сцене | Что часто видно в Profiler |
|--------|---------------------------|----------------------------|
| Спавн врагов | **`EnemySpawner.SpawnEnemy`**, encounter + волны | спайк **GC Alloc**, **Scripts** |
| Снаряды | **`RangedEnemy`** + **`Projectile`** | повторяющийся alloc при стрельбе |
| AI каждый кадр | **`EnemyBase.Update`** | стабильная полоса **Scripts** |
| Награда/поиск | **`EnemyDeathRewarder`** (`FindObjectsByType`) | пики CPU при смерти волны |
| UI | HUD, pause, win/lose | лишние обновления, если опрос каждый кадр |
| Сцены | **Build Settings**, **`LevelSequenceData`** | билд не грузит сцену → «работало в Editor» |

### 2.2. Платформы (одна таблица, без deep dive)

| | PC (класс / демо) | Mobile (идея) | Кроссплатформа |
|--|-------------------|---------------|----------------|
| Цель кадра | часто 60 FPS на среднем ПК | 30–60, прогрев, throttling | проектировать под **самый слабый** таргет |
| Память | запас больше | жёсткий лимит, kill приложения | меньше одновременных врагов/эффектов |
| CPU | можно «прощать» тяжёлый AI | проще поведение, меньше врагов | один Profiler-pass на сниженном **Quality** |
| Проверка | **exe** в классе | билд на устройство + 5 мин игры | не полагаться только на Game view |
| Билд | Windows x64 (типично) | Android/iOS — отдельные настройки | версия в **`Player Settings`** |

## 3. Пошагово (три слоя: Editor / Code / Check)

### 3.1. Подготовка сценария теста (фиксированный маршрут)

**Editor**

- Открыть **`GameScene`** (или основную gameplay-сцену проекта).
- Включить **Clear on Play** в Console.
- Записать на бумаге/в заметке **сценарий 60 секунд** (одинаковый для всех прогонов):
  1. Play из **`Bootstrap`** (не из середины уровня).
  2. MainMenu → старт игры через Loading.
  3. Движение + 3–5 атак.
  4. Запуск encounter (войти в trigger).
  5. Дождаться волны / убить нескольких врагов.
  6. (По возможности) дойти до win или lose — хотя бы один раз за сессию диагностики.

**Code**

- Убедиться, что flow старта идёт через **`Bootstrap`** → **`GameManager`** / **`SceneLoader`** (см. этапы старта игры и 9.5).
- Имена сцен в **`LevelSequenceData`** и в **Build Settings** совпадают с файлами `.unity`.

**Check**

- Один полный прогон без **красных** ошибок в Console.
- Сценарий воспроизводим: второй запуск Play даёт тот же маршрут.

### 3.3. Profiler — одна запись, четыре вкладки

**Editor**

- Play Mode → **Window → Analysis → Profiler** (или **Window → Analysis → Profiler (Standalone)** в новых версиях).
- Включить **Record** (если выключен).
- Прогнать сценарий §3.1 **60 секунд**.
- Остановить Play, **не закрывая** окно Profiler — разобрать кадры.

Смотреть **только**:

1. **CPU Usage** — доля **Scripts**, **Animation**, **Physics**, **AI** (NavMesh).
2. **Rendering** — **Batches**, **SetPass calls** (URP), пики при большом UI.
3. **Memory** — **Total Used Memory**, **GC Alloc** (спайки).
4. **Physics** — если много **Rigidbody** / trigger-коллайдеров / снарядов.

**Code** (где кликнуть в иерархии Profiler → **Scripts**)

- **`EnemyBase.Update`** — постоянная стоимость на каждого живого врага.
- **`EnemySpawner`** / **`EncounterTrigger`** — момент спавна волны.
- **`RangedEnemy`** — момент выстрела.
- **`EnemyDeathRewarder`** — пики при массовой смерти (поиск по сцене).

**Check**

- Заполнить **Profiler-заметку** (шаблон §3.4) — три наблюдения с цифрами или скрином.
- Найти **хотя бы один** спайк **GC Alloc**, совпадающий со спавном или выстрелом (если нет — описать, что доминирует CPU).

### 3.4. Три «красных флага» и критерий «достаточно хорошо»

Заполнить таблицу (в тетради, Notion или в конце этого файла):

| # | Красный флаг | Где в проекте | Что увидели в Profiler / игре | Достаточно хорошо, если… |
|---|--------------|---------------|-------------------------------|---------------------------|
| 1 | Спайн **GC Alloc** при спавне/выстреле | **`Instantiate`** в spawner / **`RangedEnemy`** | пик на кадре волны или выстрела | нет **непрерывного** роста памяти 3–5 мин; допустим краткий спайк на волне, если объяснён |
| 2 | **Scripts** «съедают» кадр | **`EnemyBase.Update`**, лишний поиск цели | высокая полоса Scripts при 5+ врагах | нет одного пустого/отладочного **`Update`** с тяжёлой логикой |
| 3 | Память только растёт | враги не **`Destroy`**, ссылки держат объекты | Total Memory ползёт вверх без плато | после 3–5 мин геймплея память **стабилизируется** (пила GC — норма, «лестница» вверх — нет) |

**Editor — микро-правка (одна, на выбор)**

Выбрать **одно** действие и повторить запись Profiler 30 сек:

- убрать **`Debug.Log`** из **`Update`** (или отключить **`showDebugLogs`** у спавнера на время теста);
- закэшировать ссылку на игрока в **`EnemySpawner`** / **`EnemyBase`** вместо поиска каждый кадр (если такой поиск есть);
- уменьшить **`maxEnemies`** или интервал волны **только для теста** сцены;
- снизить **Quality** (Edit → Project Settings → Quality) и сравнить **Rendering**.

**Code**

- Не менять публичные контракты **`IDamageable`**, encounter, save — только локальная оптимизация/отладка.
- **`Destroy(gameObject, delay)`** в **`EnemyBase`** — норма для simple-ветки; не путать с «утечкой», если объекты реально исчезают с иерархии.

**Check**

- В заметке: **«до / после»** — одно предложение, стало ли лучше по CPU/GC/ощущению фриза.

### 3.5. Memory и pooling (концепт, без обязательного pool у всех)

**Editor**

- (Опционально) преподавательский demo: сравнить simple spawn и advanced pool в отдельной ветке/сцене — **один** encounter, две записи Profiler.

**Code**

- Прочитать блок смерти в **`EnemyBase`**: если есть **`PooledEnemy`**, **`Destroy`** не вызывается — возврат в пул через подписчиков **`OnDied`**.
- **`EnemySpawner`**: комментарий в шапке — simple-ветка **без** pool/factory.
- Идея pool: **переиспользовать** объект → меньше **`Instantiate`/`Destroy`** → меньше GC и стабильнее encounter на слабых устройствах.

**Check**

- Сформулировать **одним абзацем**: зачем pool в action RPG с волнами; почему на курсе pool в **бонус**, а не в обязательном scope.

## 4. Частые ошибки и хрупкие места

- **«В Editor всё ок, exe падает или чёрный экран»** — первая сцена не **`Bootstrap`**; не все сцены в Build list; не скопирована папка **`_Data`** рядом с exe.
- **«Scene not found» в билде** — имя в **`LevelSequenceData`** / **`SceneLoader`** не совпадает с именем в Build Settings (регистр букв).
- **Profiler смотрят до encounter** — нет спайнов GC; сценарий §3.1 обязателен.
- **Путают GC-пилу и утечку** — после волны память должна **не ползти бесконечно**; если ползёт — искать неуничтоженные объекты и ссылки (список **`activeEnemies`**, события без отписки).
- **`FindObjectsByType` на каждую смерть** — краткий пик CPU; на слабом mobile при больших волнах может ощущаться как фриз (знать, не обязательно чинить на этапе).
- **Двойная смерть / двойной Destroy** — странное поведение pool и наград; Console warnings.
- **Development Build отдали как «финал»** — для защиты использовать **release** без Development (§3.10).
- **Оптимизация «всего проекта» за один вечер** — перегруз; допустима **одна** микро-правка с измерением.
- **Pooling обязателен всем** — нет; в спецификации курса pool в **бонус**; достаточно объяснения + demo teacher repo.

## 6. Что будет дальше

После 9.7 vertical slice считается **готовым к показу** с точки зрения production-гигиены. Дальнейшие темы маршрута (дополнительные модули, polish, advanced enemy branch) не отменяют требование **хранить рабочий билд** и повторять короткий smoke-test после крупных изменений. Углубление (Addressables, полный mobile pipeline, автоматические perf-тесты) остаётся вне обязательного scope курса — заголовок **«Позже»** в индивидуальных планах.
